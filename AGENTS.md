# AGENTS.md

Guidance for AI coding agents (and humans) working in this repository.

## What this is

World is a single-player, first-person destruction sandbox built in Rust on Bevy. Everything visible is made of 1/64 m voxels. The world is a sparse 64-tree rendered by ray tracing in compute shaders, never meshed. Rapier handles physics. Targets are Windows and macOS.

The full design lives in `docs/plans/engine-plan.md`. Read it before making architectural changes. Decisions made after it are recorded in `docs/decisions/`.

## Layout

| Path | Role |
| --- | --- |
| `crates/Foundation/` | Bevy-free crates: `World_Core`, `World_Gen`, `World_Cpu_Ref`, `World_Testkit` |
| `crates/Engine/` | Bevy plugins: `World_Render`, `World_Physics`, `World_Anim`, `World_Sim`, `World_Reload` (live reloading), plus `World_Testkit_Bevy` (test support) |
| `crates/Game/` | Gameplay: `World_Game` |
| `app/` | The binary: CLI, settings, startup, plugin assembly |
| `tools/` | `Xtask`, `Bake_Vox`, `Mesh_To_Voxel` (offline, never shipped) |
| `assets/` | Runtime content: WESL shaders, RON config, rigs, models, audio, UI |
| `tests/` | Workspace-level golden images, scenes and replays |
| `packaging/` | macOS and Windows packaging metadata |
| `scripts/` | Small developer and CI helpers |
| `docs/` | Plans, decisions, architecture notes, research, devlog |
| `Design/` | Concept images of the intended look, and the script that generates them (never shipped) |
| `.cargo/`, `.config/` | Cargo aliases and environment, nextest configuration |

Every folder has a `README.md` that states its permanent purpose, scope and rules. Read the README of the folder you are about to change.

## Rules

1. **Dependency direction is one way:** Foundation <- Engine <- Game <- app. Never import upward.
2. **Foundation crates have no Bevy dependency.** If something needs Bevy, it belongs in `Engine/` or higher.
3. **Rapier is named only inside `World_Physics/src/rapier`.** Swapping physics engines must touch one crate.
4. **Shared constants live in `World_Core` only.** Shader copies are generated by `Xtask` codegen, never edited by hand.
5. **The CPU 64-tree is the source of truth.** The GPU mirrors it. Never let GPU state become authoritative.
6. **Worldgen is deterministic.** Same seed and chunk coordinate give identical voxels on every machine. Saves store edits only.
7. **No meshing of the world.** Triangles are for UI, gizmos and proxy boxes only.
8. **Each Bevy crate exposes one public `Plugin` and a `prelude`.** Everything else stays crate-private unless another crate needs it.
9. **Prefer deep module folders inside the existing crates** over creating new crates. New crates are rare because hot-patching works best with few of them.
10. **Tune with data first.** Materials, physics constants and worldgen parameters go in RON files under `assets/config/`, not in code.
11. **Hash maps for lookups, ordered containers for output.** Hot-path lookups use `rustc-hash` (World_Core) or `bevy_platform` hash maps (Engine). Anything iterated to produce output, generation or saves uses `BTreeMap`, a sorted `Vec` or `indexmap`, because foldhash and hashbrown iteration order differs across platforms and runs (decision 0003 determinism).

## Naming

- Crate folders are `Pascal_Case` (`World_Render`). Package and crate names are `snake_case` (`world_render`).
- Module folders and files inside `src/` are `snake_case`.
- Top-level organizational folders are lowercase.

## READMEs are fixed

The folder `README.md` files are written once and describe intent, not contents. Do not edit them to reflect new files or progress. If a folder's purpose genuinely changes, record a decision in `docs/decisions/` first and then update that README as part of the same change.

## Large files

Binary assets (`.vox`, baked voxel files, images, audio, fonts) are stored with Git LFS, configured in `.gitattributes`. Run `git lfs install` once per clone.

## Testing expectations

- Core logic is covered by unit and property tests, checked against simple reference implementations (dense array, brute-force DDA, `World_Cpu_Ref`).
- ECS behavior is tested with a headless `App` and schedule randomization turned on.
- Physics uses deterministic replay with recorded hashes.
- Rendering is checked against golden images and exact CPU-vs-GPU hit comparisons on small scenes.
- Run the relevant tests before reporting work as done, and report failures with their output.

### How the testing engine works

Design and reasons: `docs/decisions/0001-testing-engine.md`.

- `World_Testkit` (no Bevy) has the dense reference model, proptest strategies, xxh3 hashing, replay records, golden comparison and the CPU-vs-GPU hit comparator. `World_Testkit_Bevy` has the headless `App`, schedule randomization and offscreen rendering. Use them as dev-dependencies.
- Unit tests are inline, integration and property tests go in the crate's `tests/`, cross-crate suites go in `tests/suites/` (the `world_tests` crate; register each file as a `[[test]]` in `tests/Cargo.toml`).
- Any test that needs a GPU adapter is named `gpu_...`. When no adapter exists it calls `skip_or_fail`: it prints `SKIPPED` locally and fails when `WORLD_TEST_REQUIRE_GPU=1`.
- Render tests use the software adapter by default. `WORLD_TEST_ADAPTER=gpu` uses the real GPU.
- Property tests size themselves from `world_testkit::profile`: `WORLD_TEST_PROFILE=fast` (default) or `full` (one million random edits).
- Golden files (`tests/golden`, `tests/replays`, `tests/scenes`) change only through `cargo xtask golden --update`. Review the diff and explain it in the commit. A missing golden file fails the test.
- Every new voxel structure must be checked against `DenseWorld` by implementing `VoxelModel` and calling `compare_after_edits`. Every new tracer must pass `compare_hits` against the CPU reference.
- Do not rely on system order. Run ECS tests across seeds with `for_each_seed`.

```bash
cargo xtask test              # fast profile: everything except GPU tests
cargo xtask test gpu          # only GPU tests, on the software adapter
cargo xtask test all          # everything at fast scale
cargo xtask test full         # everything at the one-million-edit scale
cargo xtask golden            # check golden files
cargo xtask golden --update   # rewrite them after reviewing the output
cargo xtask bench --save main # store a benchmark baseline
cargo xtask bench --check main --threshold 10   # fail on a >10% slowdown
cargo xtask check             # fmt, clippy -D warnings, fast tests
cargo xtask coverage          # HTML coverage in target/llvm-cov/html
cargo xtask miri              # Miri on the crates that may hold unsafe code
cargo xtask bench --instructions                       # instruction counts (gungraun, Linux + Valgrind)
cargo xtask bench --instructions --check main --threshold 5   # fail on >5% more instructions
cargo xtask fuzz [decode|round_trip] [--time SECS]     # cargo-fuzz on the decoder (nightly), 300 s each
cargo xtask mutants [-- ARGS]                          # cargo-mutants on World_Core, results in mutants.out/
cargo bench -p world_core --bench memory               # print tree memory per surface voxel and fragmentation
cargo bench -p world_core --bench workloads -- chunks   # chunk move, compaction, LZ4 and zstd throughput
cargo bench -p world_gen --bench terrain -- terrain_tree   # seed to tree for one 16 m chunk
```

- Benchmarks: `World_Core/benches/tree.rs` (microbenchmarks) and `workloads.rs` (dense overwrites, carving, coherent reads, `apply` batches, the first edit after a snapshot of a 500 MiB tree, serialization) are Criterion wall-time benches; `memory.rs` prints `stats()` figures; `instructions.rs` counts instructions with gungraun under Valgrind and is what CI gates on (`quality` workflow, `bench-instructions` job), because instruction counts are stable on shared runners and wall time is not.
- Reads must not allocate: `World_Core/tests/no_alloc.rs` uses dhat's counting allocator to check `get`, `NodeRef` walks, `same_content`, `content_hash` and snapshots. Keep it to one `#[test]`, since dhat counts every thread.
- The fuzz project (`World_Core/fuzz`, its own workspace, excluded from the main one) needs `rustup toolchain install nightly --profile minimal --no-self-update` and `cargo install cargo-fuzz --locked`. Crash inputs land in `fuzz/artifacts/<target>/`. CI fuzzes weekly.
- Mutation testing reads `.cargo/mutants.toml` and needs `cargo install cargo-mutants --locked`. Narrow a run with `cargo xtask mutants -- --file 'crates/Foundation/World_Core/src/coords/**'`. CI runs it weekly in four shards and uploads `mutants.out`.
- Instruction counts need Linux: `valgrind` and `cargo install gungraun-runner --version <the gungraun version in Cargo.lock> --locked`. On Windows use WSL.

Tools the runner expects: `cargo install cargo-nextest --locked`, `cargo install cargo-llvm-cov --locked` with `rustup component add llvm-tools-preview`, and `rustup toolchain install nightly --component miri` for Miri. Pass `--no-self-update` to `rustup toolchain install`, because a rustup self-update can fail on Windows and leave `rustup.exe` missing.

## Hot reloading

Design and reasons: `docs/decisions/0002-hot-reload-engine.md`.

- **Tuning is a config.** A tunable type implements `world_core::ConfigAsset` (`NAME`, `PATH` and `validate`, which lists every problem), lives in the crate that owns it, and is registered with `app.add_config::<T>()` (the type's `PATH`, such as `"config/x.ron"`, says which file). Systems read `Res<Config<T>>` and use change detection. Saves reload live; a file that fails to parse or validate is rejected, logged and shown in the F2 panel, and the last good value stays. `Default` must be safe and valid. Every file in `assets/config/` must be registered by some plugin (a test checks this).
- **Setup that should follow code edits is reloadable.** Register it with `app.add_reloadable_systems(|| my_setup)` and tag what it spawns with `ReloadScoped`. It runs at startup and again after every `CodeReloaded` (written for each hot-patch, by F5, or by tests), after the tagged entities are despawned.
- **Never combine `dynamic_linking` with hot-patching.** `cargo xtask hot` builds with `--no-default-features --features hotpatch`. Always start dx through xtask: on Windows it works around dx 0.7.10 linking bugs (a linker shim, the Visual Studio environment, stale fat archives), all in `tools/Xtask/src/hot/windows.rs` and `link_shim.rs` (see decision 0002). `.cargo/config.toml` selects `rust-lld` for ordinary builds.
- **Shaders hot-reload** through the asset server, including WESL imports (`import package::shaders::...`).
- Hot-patching cannot change struct layouts or system signatures; those need a restart. Only systems (and observers) pick up patched code: a config's `validate`, its asset loader and other code reached through stored function pointers keep the old code until restart.
- Reloadable setup despawns and respawns its `ReloadScoped` entities, so their `Entity` ids change on every reload (F5 or a patch). Never keep one across frames; query for a marker component instead. Resources that setup inserts are not reset.
- Fields of a config that nothing reads yet are marked "not used yet" in the RON file, so editing them is not mistaken for a live change.

```bash
cargo xtask dev            # cargo run with dev feature: asset, shader and config reload, panels
cargo xtask hot            # dx serve --hot-patch: also patches Rust systems live
cargo xtask hot --smoke    # automated end-to-end hot-patch check (edits and restores a probe)
cargo xtask test reload    # every hot-reload test, GPU shader reload and the hotpatch bridge
```

`dx` must match the `subsecond` version in `Cargo.lock` (0.7.10): `cargo install dioxus-cli --version 0.7.10 --locked`.

## The streamed world

Design and reasons: decisions 0006 to 0009.

- The world tree is stored per chunk: the subtree under each level-4 node (1024 voxels, 16 m) has its own arenas. A chunk-level or larger region can be not resident; reads report it (`lookup` returns `None`) and edits there fail with `EditError::NotResident`.
- Build trees bottom-up through a `RegionSource` (`VoxelTree::from_source`, `build_region`), never with one `set` per voxel. Move finished chunks between trees with `take_chunk` and `insert_chunk` (O(1)).
- World_Game's `residency` domain owns the world (`StreamedWorld`): loading around the player, saving edited chunks as overlays in region files, the edit log, the warm and coarse tiers. Gameplay edits go through it, never straight to a tree. Tune it in `assets/config/residency.ron`; terrain lives in `assets/config/terrain.ron`.
- Saves are in `saves/` (git-ignored). Deleting it resets the world to the seed.
- Terrain generation is bit-exact on every platform (decision 0008): plain `f32`, no `mul_add`, no platform math functions, no runtime SIMD dispatch. World_Gen's golden hashes run on Windows, macOS arm64 and macOS x86_64.

## Building and running

The toolchain is pinned in `rust-toolchain.toml` (Bevy 0.20 needs Rust 1.97.1 or newer); rustup installs it on first use. The first build compiles about 380 crates and takes roughly 12 minutes. Later builds are incremental.

```bash
cargo run                          # opens the window; backend and tier are chosen automatically
cargo run -- --list-adapters       # print every GPU found with its tier verdict, then exit
cargo run -- --backend vulkan      # force dx12, vulkan or metal (also reads WGPU_BACKEND)
cargo run -- --mac-floor           # tier B, 720p internal, 1 GiB brick pool, 4 worker threads
cargo run -- --exit-after-frames N # quit cleanly after N frames, for automated runs
cargo xtask dev                    # cargo run with the developer panels (F1 inspector, F2 configs, F5 re-run setup)
cargo test --workspace
```

The default `dev` feature of `app` enables dynamic linking, asset hot reload and the developer panels. The `hotpatch` feature replaces it for `dx`. Release builds use `--no-default-features`. `.cargo/config.toml` points Bevy at the top-level `assets/` folder.

Backend and tier are decided before Bevy creates the GPU device: `World_Render::tier` probes adapters, `app/src/startup` picks one and tells Bevy exactly which adapter to use. `Xtask` has the test, golden, bench, check, coverage, miri, fuzz, mutants, dev and hot commands; its codegen and packaging commands and the release CI come later. `.github/workflows/test.yml` runs formatting, clippy (including the hotpatch and release feature sets) and every test on Windows; on macOS it runs the non-GPU tests and builds a universal binary for Apple Silicon and Intel. The hot-patch smoke test runs weekly and on manual dispatch. `.github/workflows/quality.yml` (not required checks) counts World_Core's instructions on Linux for every core change and compares them with main, and fuzzes the decoder and runs mutation testing weekly.
